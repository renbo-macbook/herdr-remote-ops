01

Prepare both devices

Do these checks before changing your Mac's network services.

P1

Verify Mac requirements and existing agent setup

Use macOS 13 Ventura or newer with current Tailscale (minimum according to Tailscale's current macOS variant comparison). The iPhone needs iOS 18 or newer for the current Moshi App Store release. Install Homebrew on the Mac from brew.sh if necessary.

Mac Terminal — read-only
sw_vers -productVersion
uname -m
whoami
brew --version

Copy the result of whoami to the Mac username field. Before starting remote setup, make sure your normal Hermes and Codex commands work locally.

P2

Secure the iPhone and Tailscale identity

Use an iPhone running iOS 18+, with a strong passcode and Face ID/Touch ID. Keep Moshi, Tailscale and iOS updated. Enable MFA/passkeys for the account used to sign in to Tailscale and preserve account recovery methods.

Have physical access to the Mac for initial pairing. Do not enter passwords, private SSH keys, tokens or QR codes into this HTML file.

P3

Choose which macOS account runs Herdr

Simplest: use your existing non-shared Mac account so Hermes, Codex, Git repositories and credentials remain available. Stronger isolation: create a dedicated standard account, but move/configure its projects and agent credentials there first. In either case, grant Remote Login to only this account.

A remote SSH session has the permissions of the account you log into. Approving agent commands from your phone can still cause local file writes or network actions. Keep your existing Hermes/Codex review and approval controls in place.
02

Connect Mac and iPhone with Tailscale

Make the private network work before configuring SSH.

T1

Install Tailscale on the MacBook

  1. Download the official Standalone macOS variant.
  2. Install it, approve macOS VPN/system-extension prompts, and sign in using your secured identity-provider account.
  3. Do not install the Standalone and Mac App Store variants at the same time.

The macOS Standalone client is recommended here. You are using macOS's SSH server through Tailscale, not the separately configured Tailscale SSH server.

T2

Install Tailscale on the iPhone

Install Tailscale for iOS from its official link. Sign in to the same tailnet, approve the VPN prompt and turn the connection on. You can leave cellular data enabled. For now, keep the Mac reachable locally.

T3

Record each device's address

Open Tailscale → Machines. Confirm both devices are connected; copy their 100.x.y.z addresses and your Mac's full MagicDNS name into the form above. Check that Mac and iPhone addresses are different.

Optionally enable device approval under Device management and approve any pending device. Keep track of Tailscale node-key expiry and renewal dates. Reauthentication happens in the Tailscale app, not in Moshi. Reauthenticate both devices before travel, while you still have local access to your Mac. An expired Mac key can make remote recovery difficult; see the official key-expiry guidance before changing expiry policy.

Device approval prevents unapproved new devices joining. It does not itself restrict an already approved device to port 22. The narrow access grant comes later.
T4

Secure and periodically review your tailnet

These Tailscale console checks are low maintenance but useful even for a one-person setup:

  • Security contact: under tailnet contact preferences, verify the security-notification address points to an inbox you monitor.
  • Unused credentials: check Keys and revoke unused authorization keys, API access tokens and OAuth clients. Do not revoke credentials whose purpose you have not established.
  • Audit logs: inspect configuration audit logs after substantial changes or when you suspect unauthorized modifications.
  • Maintain Tailscale updates on both devices, and remove lost or retired machines promptly.

Tailscale security guidance gives the rationale and current menu locations.

03

Configure macOS Remote Login

Do not disable passwords until the iPhone's key login has been proven to work.

S1

Enable Apple's SSH server for one user

On the Mac open System Settings → General → Sharing → Remote Login and select:

SettingValue
Remote LoginOn
Allow access forOnly these users
Allowed userYour selected Mac account only; remove any broad Administrators entry
Allow full disk access for remote usersOff unless strictly required for your specific folders

Make sure your router does not forward 22, 5900 or 445 to the Mac. SSH might still accept connections on your home LAN, which is why keys and access restrictions matter.

S2

Confirm Tailscale SSH is not intercepting port 22

macOS SSH over Tailscale and Tailscale SSH are different. This guide needs Apple's OpenSSH server to handle the iPhone's key. Moshi Easy Pair may refuse to run if Tailscale SSH intercepts the connection.

The recommended Tailscale Standalone macOS app cannot act as a Tailscale SSH server, so this should already be off in the intended configuration. If you previously used the open-source tailscaled variant or changed your setup, check it explicitly:

Mac Terminal — read-only, current app variant
TAILSCALE_BE_CLI=1 /Applications/Tailscale.app/Contents/MacOS/Tailscale debug prefs | grep -i RunSSH

If the output includes RunSSH: true (or an equivalent true value), stop and disable Tailscale SSH in the actual Tailscale installation before pairing. For the open-source CLI variant the documented command is tailscale set --ssh=false. Confirm that you are not dependent on that service first. A missing field is not proof by itself; verify the variant and allow moshi-hook host setup to run its own preflight.

TAILSCALE_BE_CLI=1 is a documented Tailscale macOS CLI override: it forces the app executable to print command output rather than launch its GUI. It is intentional, not a typo. If the standalone installer provided the tailscale shell command, you can instead run tailscale debug prefs. Tailscale CLI reference.

Tailscale SSH server documentation · Moshi Tailscale guide.

S3

Record the Mac SSH host-key fingerprint

Record the host's Ed25519 SHA256 fingerprint locally. Compare it with the identity recorded in Moshi during pairing; do not blindly accept a changed host key.

Mac Terminal — read-only
ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub

Moshi Easy Pair pins the host fingerprint in the QR code when moshi-hook is version 0.4.32 or later. Verify your installed version before relying on QR fingerprint pinning. Moshi authentication and host-key documentation.

04

Set up Moshi on your iPhone

Primary path: Moshi Easy Pair (QR). It creates the SSH key and saved connection for you. Manual setup is only a fallback.

I1

Install Moshi and the host pairing helper

Install Moshi for iPhone. Open the app and locate Easy Pair in onboarding. On the Mac, install the official Moshi helper:

Mac Terminal — official Moshi Homebrew tap
brew tap rjyo/moshi
brew trust rjyo/moshi
brew install moshi-hook
moshi-hook --version

If Homebrew prompts you to inspect or trust the tap, check that it is the expected project. The helper handles SSH Easy Pair and can later support optional agent notifications.

Do not install Mosh transport just to get SSH workingHerdr itself preserves terminal panes. mosh-server and tmux are optional for the plain-SSH + Herdr workflow, although particular Moshi helper versions may request them in their pairing preflight. If moshi-hook host setup specifically asks for these dependencies, install with brew install mosh tmux and retry; otherwise leave them out.

Cost: SSH is available in Moshi Free. Mosh transport and automatic Herdr/tmux reattachment are currently Pro features; no paid upgrade is necessary for manual Herdr reattachment.

I2

Pair the iPhone using Moshi's QR code

Confirm Tailscale is connected on both devices, Remote Login is enabled and step S2 has been checked. Run the helper locally on the unlocked Mac:

Mac Terminal — Easy Pair
moshi-hook host setup
  1. Inspect the proposed destination: use your Mac's full Tailscale MagicDNS name or 100.x.y.z address, not its public or LAN address.
  2. In Moshi on the iPhone, scan the QR code via Easy Pair.
  3. Moshi generates the SSH private key on the phone, transfers only the public key into the Mac user's authorized_keys, and creates the saved connection.
  4. For moshi-hook ≥ 0.4.32 the QR also pins the SSH host fingerprint. Compare it independently with S3.
Treat the QR as a temporary access credentialAnyone who scans the QR while it is valid may claim SSH access. Do not screenshot or share it, and close pairing as soon as your phone is paired.

Important: SSH Easy Pair is distinct from moshi-hook pair --token, which pairs the optional agent notification service, not the SSH login.

I3

Verify the first SSH connection in Moshi

Open the saved host in Moshi. Force Connection type: SSH for the first test rather than Auto/Mosh. Check host is the MagicDNS/100.x address, port 22, correct Mac short username and the key from Easy Pair.

Confirm the SSH host fingerprint from step S3. Connect and verify the remote terminal is your Mac:

Moshi terminal on iPhone — read-only
whoami
pwd
uname -s

Expected results: the selected Mac account name, an expected working directory, and Darwin. Keep a separate local Terminal open on the Mac while you harden SSH in the next section.

I4FALLBACK

Fallback: set up your SSH key manually

Use this only when the QR flow does not work. In Moshi create a new connection using the Mac's MagicDNS name or Tailscale IPv4, port 22, the Mac short username, and connection type SSH. Generate an Ed25519 key in Moshi and copy only the public key to the Mac.

Mac Terminal — install public key manually
umask 077
mkdir -p ~/.ssh
nano ~/.ssh/authorized_keys
chmod 700 ~/.ssh
chmod 600 ~/.ssh/authorized_keys

In nano, add the full public key on its own line, save with Ctrl+O and exit with Ctrl+X. Preserve your existing authorized keys. Never paste the iPhone's private key into this guide, any chat or a repository.

If Easy Pair already worked, leave this fallback unchecked. It does not count toward required progress.

05

Harden SSH and Tailscale access

Do these after successful Moshi key login. Keep physical Mac access while testing; never harden SSH blindly.

H1

Verify the SSH config supports include files

Apple's OpenSSH configuration can include /etc/ssh/sshd_config.d/ snippets. Check before creating one. If the output does not include that directory, stop this step and consult your macOS version's SSH documentation rather than assuming the snippet is active.

Run on Mac
grep -nE '^[[:space:]]*Include[[:space:]]+' /etc/ssh/sshd_config
ls -la /etc/ssh/sshd_config.d/ 2>/dev/null

The order of first-seen sshd settings matters. The effective-configuration test in H3 is mandatory.

H2

Disable SSH passwords — only after key login works

Create a focused early-loading drop-in on the Mac. This is deliberately not a rewrite of Apple's main config. Test syntax before opening any new remote connection.

Run on Mac
sudo tee /etc/ssh/sshd_config.d/050-herdr-key-only.conf >/dev/null <<'EOF'
PubkeyAuthentication yes
PasswordAuthentication no
KbdInteractiveAuthentication no
PermitRootLogin no
EOF
sudo /usr/sbin/sshd -t

If sshd -t reports an error, do not disconnect; fix the file or undo it using the rollback below. A successful syntax check alone does not prove the settings are active.

Rollback (only if needed)
sudo rm /etc/ssh/sshd_config.d/050-herdr-key-only.conf
sudo /usr/sbin/sshd -t
H3

Inspect the effective SSH settings and reconnect

Run the first command locally. Confirm all four relevant lines report the expected values, particularly passwordauthentication no and kbdinteractiveauthentication no.

Run on Mac
sudo /usr/sbin/sshd -T -C user={{username}},host=localhost,addr={{phoneip}} | grep -E '^(pubkeyauthentication|passwordauthentication|kbdinteractiveauthentication|permitrootlogin) '
Expected values
pubkeyauthentication yes
passwordauthentication no
kbdinteractiveauthentication no
permitrootlogin no

Close the iPhone connection and open a brand-new SSH connection. It must still work. If the effective values are wrong, stop and investigate before relying on the hardening.

H4

Restrict Tailscale traffic to your iPhone → Mac SSH

Open Tailscale → Access controls. The example policy below is appropriate only for a dedicated tailnet where no other access is required. It permits the iPhone to open TCP port 22 on the Mac, but no other ports or device-to-device paths.

Example tailnet policy (JSON)
Enter both Tailscale IP addresses above to generate the policy.
Do not blindly overwrite an existing policyRemove or narrow any broad allow-all acls and grants rules, because grants are additive, not overriding. If other devices, Tailscale SSH policies, groups, tags or subnet routes exist, preserve their required rules and merge this grant carefully. Back up your policy first. Tailscale rules do not filter the Mac's LAN interface.

Save only after the console validates the policy. Open a fresh iPhone SSH connection afterward. Keep local access available until it works. Tailscale-granted IP paths allow the matching devices to ping one another even if only TCP 22 is listed.

H5 OPTIONAL · ADVANCED

Restrict the phone's SSH public key to its Tailscale IPv4

After the base setup works, you can further limit that one key to connections originating from the iPhone's tailnet IPv4. Edit its existing line in ~/.ssh/authorized_keys to begin with the generated prefix, followed by a space and the existing complete public key.

Prefix to add before your phone's public key
from="{{phoneip}}"

For example, the resulting single line would be from="100.x.y.z" ssh-ed25519 AAAA... phone-key. This is an OpenSSH source-IP restriction, not a firewall. Retest SSH immediately from Moshi over Tailscale, and remember that Tailscale device re-enrollment can change the iPhone's source IP. Do not accidentally modify keys for other devices.

H6

Test that password-only SSH authentication fails

First, reconnect from Moshi using the saved key; it must work. Then run the negative test below locally on the Mac. It intentionally disables SSH public-key authentication for this one command.

Mac Terminal — should reject password-only SSH
ssh -o PubkeyAuthentication=no -o PreferredAuthentications=password,keyboard-interactive {{username}}@127.0.0.1

The expected outcome is permission denied, not a password prompt that grants login. The effective-config test in H3 is authoritative; a refused local network connection by itself is not sufficient evidence.

After applying the Tailscale grant in H4, verify Moshi still connects on cellular data. Tailscale policy does not block ordinary LAN SSH; use the optional host firewall guidance if strict Tailscale-only reachability is mandatory.

07

Keep the Mac reachable

Working SSH is only useful when the Mac remains powered on and awake.

L1

Review power, sleep and lid behavior

  • Connect reliable external power. In System Settings → Battery / Options, review relevant sleep and wake settings for your macOS version.
  • Prevent automatic system sleep while you need agents; screen-off is fine.
  • Keep the MacBook lid open, unless you have a tested, supported closed-display configuration. caffeinate does not guarantee operation with the lid closed.
  • Wake for network access is helpful in some scenarios but is not a guarantee that remote SSH over Tailscale can wake a sleeping laptop.
Optional diagnostic — run on Mac
pmset -g custom
pmset -g assertions

For a temporary local test, run caffeinate -i in a Mac Terminal and keep that process running. Do not assume the session survives a reboot or that it overrides lid closure.

L2

Understand reboot and logout limits

The normal macOS Tailscale GUI client runs within a user login session. After restart or logout, particularly with FileVault, remote access may be impossible until the Mac is unlocked and signed in locally. Herdr can restore layout/state in supported cases, but arbitrary running processes do not survive a full reboot. Avoid remote reboots without a recovery route.

For critical unattended workIf you need reliable recovery after power failure and reboot, a permanently powered host with an appropriate unattended VPN/service architecture is more suitable than a standard MacBook + Tailscale GUI setup.
L3

Do the full test over cellular data

  1. Leave the Mac awake, powered and signed in with Tailscale connected.
  2. Disable iPhone Wi-Fi and confirm cellular data works.
  3. Open Tailscale on the phone and confirm the tailnet is connected. If either device requests reauthentication, complete it inside the Tailscale app (or its login flow), not in Moshi.
  4. In Moshi, connect to the Mac's MagicDNS name or its 100.x.y.z address and run herdr (Moshi Free), or use the Herdr session picker (Moshi Pro).
  5. Detach, close Moshi, lock the phone for a minute, reconnect and verify the same panes and agent processes remain.
Mac Terminal — optional network route test
TAILSCALE_BE_CLI=1 /Applications/Tailscale.app/Contents/MacOS/Tailscale ping {{phoneip}}

This command tests Tailscale's path from the Mac to your iPhone while the phone is connected. via DERP(region) means an encrypted relay; a peer IP:port means a direct path. A DERP result is not an SSH security failure, though performance may be slower. Tailscale may start relayed and then find a direct path. If ping works but Moshi cannot connect, examine SSH, permissions and the TCP 22 grant.

If you require port 22 to be unreachable on every LAN interface, develop and test a host-level PF/firewall ruleset for your actual interfaces and OS version, with local rollback access. The macOS application firewall alone is not a substitute for a verified per-interface/per-source rule. This guide deliberately does not prescribe a generic PF paste-and-run command that could lock you out.

O5 OPTIONAL

Optional remote files, screen sharing and alternative SSH clients

Keep these off unless necessary. Herdr only needs SSH. SFTP and scp already use port 22, so they do not require enabling macOS File Sharing.

  • Transfer files: use an SFTP-capable client with its own SSH key and an appropriately scoped Tailscale grant. Do not expose your home folder over SMB for this.
  • Screen Sharing: enable macOS Screen Sharing only when needed, limit it to the intended account and allow port 5900/tcp in a suitable tailnet grant only for the specific viewing device. An iPhone needs a separate compatible VNC viewer; do not forward port 5900 on your router.
  • SMB File Sharing: avoid it for this setup. If later required, share only a dedicated folder and grant 445/tcp solely to authorized devices. Never expose SMB to the internet.
  • Alternative SSH apps: another SSH client with Ed25519 keys can work over Tailscale, but Moshi's QR pairing, Herdr controls and hook features are not portable to every client.
09

Recovery and troubleshooting

X1

Prepare for a lost phone before travelling

  1. Keep a second trusted admin route to the Tailscale console (another authenticated device or recovery codes).
  2. On loss, remove the iPhone from Tailscale → Machines to revoke its access.
  3. On the Mac, remove that phone's line from ~/.ssh/authorized_keys; preserve other keys.
  4. Use Apple's Find My to lock/erase the phone. Review the identity-provider account's login sessions; rotate credentials if compromise is suspected.

Do not rely on normal node-key expiry as an immediate lost-device revocation mechanism.

SSH stalls or Moshi Easy Pair refuses to connect

Check section S2. A previously enabled Tailscale SSH server can intercept TCP port 22 in the tailnet and conflict with traditional SSH keys. The recommended macOS Standalone client cannot itself serve Tailscale SSH; check whether you are actually using the open-source tailscaled variant. Re-run moshi-hook host setup after resolving the conflict.

Moshi worked yesterday but cannot reach the Mac today

First open the Tailscale app on the iPhone and verify its VPN is connected and authenticated. Check the Mac's status and device key expiry on Tailscale → Machines. Reauthentication prompts belong to Tailscale, not Moshi. If the Mac's tailnet key expired while you are away, you may need local access or the admin-console temporary-extension recovery procedure. Do not run tailscale up --force-reauth over your only remote session; it can sever that connection.

Tailscale ping reports DERP, relay or a slow connection

From the Mac, run TAILSCALE_BE_CLI=1 /Applications/Tailscale.app/Contents/MacOS/Tailscale ping IPHONE_TAILSCALE_IP, replacing the address. The TAILSCALE_BE_CLI=1 prefix is an official macOS CLI override, not an extra installation requirement. via DERP(region) is a valid encrypted relay, not a failed VPN. A direct IP:port path is typically faster. Tailscale may initially use DERP and then upgrade to a direct path. Use Tailscale's relay troubleshooting if performance matters.

SSH times out from cellular data

Verify Mac is awake, lid is open, Tailscale connected on both devices, phone Wi-Fi is off, Mac IP is correct, Remote Login is on, and the access grant permits TCP 22. A sleeping or logged-out Mac will defeat correct SSH credentials.

SSH says “Permission denied (publickey)”

Check username, key chosen by your iPhone SSH app, exact public key in Mac ~/.ssh/authorized_keys, permissions (700/600), Remote Login allowed-user list, and any optional from="..." key prefix. Confirm the phone's tailnet IP has not changed.

Host fingerprint changed unexpectedly

Stop. Compare against the host fingerprint saved from the Mac, and only accept a new key if you independently verified a legitimate host reinstallation or host-key rotation. Never disable StrictHostKeyChecking simply to silence the warning.

Herdr command not found over SSH

Check command -v herdr from an ordinary local Mac Terminal and from the phone's interactive SSH session. Your login shell may not include Homebrew paths. Resolve the PATH for your shell rather than disabling SSH checks.

Herdr looks empty or stops on disconnect

Confirm you started agents inside Herdr panes and reattached to the same macOS account and named/default session. Detach with Ctrl+B then Q. A reboot or deliberate herdr server stop does not preserve arbitrary running programs.

SSH works; Mosh fails

Use plain SSH as the baseline. For Mosh verify mosh-server in PATH and whether the Tailscale grant allows UDP 60000–61000. Not all mobile clients implement Mosh; no Mosh configuration is necessary to use Herdr TUI.

A valid tailnet grant did not restrict access

Inspect the entire policy file for broad existing acls or grants entries, since they combine additively. Remember Tailscale policy does not govern ordinary LAN traffic. Your host may still accept LAN SSH using valid keys.

SSH password-login test does not fail

Stop relying on the intended hardening. Check the Include directive and run sshd -T using the matching user/source context. A syntactically valid snippet may be ignored or superseded; investigate the effective configuration before calling setup complete.
